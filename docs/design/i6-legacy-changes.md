# I6 设计：发现回退期间在 0.1.x 里做的改动

对应 [兼容策略](../compatibility.md) 第 3.3 节和第 7 节的 I6。

## 1. 问题

0.2.x 只在 `accounts.json` 不存在时从 `gp.secrets` 迁移一次，之后不再读 `gp.secrets`。于是下面这个流程会出问题：

1. 用户从 0.1.x 升级到 0.2.x，`accounts.json` 生成，`gp.secrets` 原样保留。
2. 用 `rollback.sh` 回退到 0.1.x（默认不恢复数据，`accounts.json` 留在原处）。
3. 在 0.1.x 里新增、删除账号，或者用同一个名称重新添加（0.1.x 会直接覆盖同名账号的 URL）。这些改动写进 `gp.secrets`。
4. 再次运行 `install.sh` 升级。`accounts.json` 已经存在，迁移被跳过，脚本只显示「沿用已有数据：N 条记录」。**第 3 步的改动在新版里看不到，也没有任何提示。**

更严重的是第 5 步：用户确认新版正常后运行 `cleanup.sh`。它会删除 `gp.secrets` 和所有安装备份，而第 3 步新增的账号，除了用户自己的导出文件或 Time Machine 备份，只存在于这两处。`cleanup.sh` 只在「新版账号数少于旧版」时提醒，用户在新版里也加过账号的话，这条提醒不会出现。**结果是这个账号的密钥被永久删除。**

## 2. 目标

- 不再悄悄忽略 0.1.x 在迁移之后做的改动：启动时发现，列出来，由用户决定。
- 不丢数据：导入只新增账号，不覆盖、不删除新版里已有的账号。
- 不产生新的明文密钥副本。
- 没有改动时，用户完全感觉不到这个功能。
- 在改动处理完之前运行 `cleanup.sh`，会明确警告哪些账号将被永久删除，由用户决定是否继续。

不做的事：

- 不做 0.1.x 和 0.2.x 之间的双向同步。0.2.x 仍然**从不写入** `gp.secrets`，回退的安全性保持不变。
- 不处理 0.2.x 里做、0.1.x 看不到的改动。这个方向已经有 `rollback.sh` 的提醒，用户可以在回退前导出 `.secrets`。

## 3. 为什么需要「基线」

只比较 `gp.secrets` 和 `accounts.json` 是不够的。`gp.secrets` 里有、`accounts.json` 里没有的账号，可能是回退期间在 0.1.x 里新加的，也可能是用户在 0.2.x 里**故意删掉**的（0.2.x 不写 `gp.secrets`，删掉的账号会一直留在里面）。两种情况看起来一模一样，后一种如果导入，等于把用户删掉的账号又找回来。

所以要在迁移时记下 `gp.secrets` 当时的样子，称为**基线**。之后拿当前的 `gp.secrets` 和基线比，差异才是 0.1.x 做的改动。

也不能只比较文件的校验值。0.1.x 每次保存都会把整个字典重新写一遍，而 Swift 字典的遍历顺序每次启动都不一样，内容没变时文件字节也可能不同。在 0.1.x 里导入一个全是已有账号的备份，同样会重写文件。所以要逐条比较解码后的内容。

## 4. 方案

### 4.1 基线文件 `legacy-baseline.json`

放在数据目录里，和其他数据文件一样原子写入，权限 `0600`：

```json
{
  "version": 1,
  "source": "gp.secrets",
  "recordedAt": "2026-10-21T08:00:00Z",
  "entries": {
    "GitHub:alice": "1f0c…（64 位十六进制）"
  }
}
```

- `entries` 的键是账号名称，值是这个账号 otpauth URL 的指纹：`SHA-256("gp-legacy-v1\n" + URL)` 的十六进制。只用来判断 URL 有没有变，**不保存密钥，也不保存 URL**。
- 指纹不会泄露密钥：TOTP 密钥一般有 80 位以上的随机性，无法从哈希反推。基线和 `gp.secrets` 放在同一个目录、权限相同，能读到基线的人本来就能读到 `gp.secrets`。
- 0.1.x 不认识这个文件，没有 I6 的 0.2.x 版本也会忽略它。
- `source` 和 `version` 留给以后：数据格式再升级时（比如 `accounts.json` 换成 `accounts-v2.json`），可以用同样的办法为旧文件记基线。这次只实现 `gp.secrets`。

### 4.2 什么时候写基线

| 时机 | 做法 |
|---|---|
| 从 `gp.secrets` 迁移时 | 生成 `accounts.json` 后，用迁移所用的同一份内容记基线 |
| 启动或运行 `--migrate-data` 时，`gp.secrets` 存在但没有基线 | 说明是 I6 之前迁移的（目前只有内测同事）。用当前的 `gp.secrets` 记基线，**不提示**。限制：在此之前 0.1.x 做的改动发现不了（见决策点 4）。这一步和迁移一样放在 `prepareDataDirectory` 里 |
| 用户处理完提示（导入或忽略）后 | 用当前的 `gp.secrets` 更新基线，同样的改动不再提示 |
| App 启动时发现了差异，但没有一条需要处理（例如都已在新版里） | 静默更新基线。`--migrate-data` 不做这一步 |

基线读不懂时，当作没有基线处理：把原文件改名为 `legacy-baseline.json.unreadable-<时间>` 保留，再重新记录。它不含账号数据，丢失的代价只是少一次提示，所以不必像 `accounts.json` 那样拒绝启动。

### 4.3 比较规则

设基线为 B（名称 → 指纹），当前 `gp.secrets` 为 L（名称 → URL），新版账号为 A。

**第一步：找出 0.1.x 的改动。**

| 情况 | 判定 |
|---|---|
| 名称在 L 里，不在 B 里 | 0.1.x 新增 |
| 名称在两边都有，指纹不同 | 0.1.x 改过（同名重新添加） |
| 名称在 B 里，不在 L 里 | 0.1.x 删除 |

**第二步：对照新版现有的账号，决定怎么处理。**

| 0.1.x 的改动 | 新版里的情况 | 处理 |
|---|---|---|
| 新增或改过，URL 为 u | 已有某个账号的 URL 也是 u（不管叫什么名字） | 已经在新版里了，跳过。例如回退前从新版导出、再导入了 0.1.x |
| 同上 | 没有 URL 为 u 的账号，但有同名账号 | **名称冲突**：以「名称 (0.1.x)」导入，两条都保留（决策点 1） |
| 同上 | 都没有 | 用原名称导入 |
| 删除 | 新版里有同名账号，且 URL 和迁移时一样 | 告知用户，不自动删除（决策点 2） |
| 删除 | 新版里已经没有，或者改过 | 跳过 |

导入的账号按名称排序后追加到列表末尾，不改变前 10 个账号的快捷键。「名称 (0.1.x)」也被占用时，依次尝试「名称 (0.1.x 2)」「名称 (0.1.x 3)」。

`gp.secrets` 不存在（例如已经运行过 `cleanup.sh`）时什么都不做。`gp.secrets` 读不懂时跳过比较，不阻止启动：此时 `accounts.json` 才是数据来源，`gp.secrets` 只是旧文件。

### 4.4 提示界面

启动时发现需要处理的改动，弹出一个窗口（和「管理」窗口一样用 SwiftUI）：

> **回退期间，旧版本改动过账号**
>
> 你在使用 GoldenPassport 0.1.x 期间，它的数据文件 `gp.secrets` 有以下改动。新版本不会自动同步这些改动，请选择要导入的账号。
>
> ☑ 新增：GitHub:bob
> ☑ 改过：AWS:alice → 将以「AWS:alice (0.1.x)」导入，原来的账号保留。请确认哪一个能生成正确的验证码，再删掉另一个。
>
> 以下账号在旧版本里被删除了，新版本里仍然保留。如果不再需要，可以在「管理」里删除：Aliyun:carol
>
> [忽略这些改动]　[稍后]　[导入所选]

- **导入所选**：导入勾选的账号，更新基线，提示「成功导入 N 条记录」（沿用「导入」菜单的提示）。没勾选的改动同样不再提示。
- **忽略这些改动**：确认后更新基线，以后不再提示这些改动。
- **稍后**：关闭窗口。菜单最上方显示「处理旧版本的改动（N）…」，下次启动时再次弹出。
- 只有删除、没有可导入的账号时，窗口里只有告知部分，按钮是「知道了」（更新基线）和「稍后」。
- 界面只显示账号名称，不显示 URL 或密钥。文字全部按现有方式做中英文本地化，约 12 条。

### 4.5 安装和清理脚本

- `--migrate-data` 的报告增加 `legacy_imports=<可导入的数量>`，以及每条 `legacy_change=<added|changed|removed>:<名称>`，只有名称。这一步只读，不更新基线（缺基线时按 4.2 记录除外）。
- `install.sh`：有任何改动时提示「回退期间，旧版本改动了 N 个账号，GoldenPassport 启动后会提示你处理」。
- `cleanup.sh`：有**可导入**的账号时，在要删除的内容下方醒目警告，列出这些账号的名称：「回退期间旧版本改动过 N 个账号，还没有导入新版本。它们的密钥只在 gp.secrets 和安装备份里，清理后将永久丢失。建议先打开 GoldenPassport 按提示导入，再运行清理。」之后照常要求输入 `yes`，用户仍然可以继续（决策点 5）。只有删除时不警告：那些账号新版本里都还在，删掉 `gp.secrets` 不会丢东西。清理时把 `legacy-baseline.json` 和 `gp.secrets` 一起删除。
- `rollback.sh`：在现有提醒后补一句「回退后在旧版本里做的改动，再次升级时 GoldenPassport 会提示你导入」。

### 4.6 需要同步修改的文档

- 兼容策略：第 1 节加上 `legacy-baseline.json`；第 2 节加一条保护；第 3.3 节把「目前也没有任何提示」改为 I6 的做法；第 7 节 I6 改为已完成。
- 两份 README：「回退」一节说明再次升级时会提示导入；数据目录的文件列表加上基线文件。
- 内测说明：如果发 beta.3，补上这一条。

## 5. 考虑过但不采用的做法

| 做法 | 不采用的原因 |
|---|---|
| 比较 `gp.secrets` 的文件校验值 | 0.1.x 每次保存时字典顺序都可能不同，内容没变也会误报；而且只能知道「变了」，列不出变了什么 |
| 直接把 `gp.secrets` 里新版没有的名称导入 | 会把用户在 0.2.x 里删掉的账号找回来；同名账号改过 URL 的情况会被漏掉 |
| 0.2.x 同时写 `gp.secrets`，保持两边一致 | 违反「0.2.x 从不修改 `gp.secrets`」的原则，回退就不再安全 |
| 只在 `install.sh` 里检查 | 手动安装的用户覆盖不到；脚本也解析不了 NSKeyedArchiver 格式 |

## 6. 测试

单元测试（`GoldenPassportCore`）：

1. 迁移时生成基线，基线里只有名称和指纹：文件内容里找不到任何密钥或 URL。
2. `gp.secrets` 内容没变、只是字典顺序不同（重新存档）时，不提示。
3. 0.1.x 新增的账号会被列出；导入后基线更新，再检查时不再提示。
4. 同名账号 URL 改过时以「名称 (0.1.x)」导入，原账号不变；后缀被占用时依次递增。
5. 0.1.x 删除的账号只告知，新版里的账号不被删除。
6. 新版里已有相同 URL 的账号（任何名称）时跳过。
7. 在 0.2.x 里删掉、`gp.secrets` 里还在但没改动的账号，**不会**被列出（这是需要基线的原因）。
8. 没有基线时静默记录，不提示。
9. `gp.secrets` 读不懂时跳过比较，不报错，`accounts.json` 照常加载。
10. 基线读不懂时改名保留并重新记录。
11. `--migrate-data` 的报告列出待处理的改动，运行前后基线不变。

脚本测试（用 `GP_*` 环境变量指向临时目录）：回退后在 `gp.secrets` 里加一个账号，再运行 `install.sh` 能看到提示；`cleanup.sh` 列出这个账号并警告，不输入 `yes` 时什么都不删，输入 `yes` 后照常清理；只删账号时 `cleanup.sh` 不警告；清理时一并删除基线文件。

界面测试：用隔离的探针 App 和假账号，分别在中文和英文下检查提示窗口、导入结果和「稍后」后的菜单项。

## 7. 决策

2026-10-21 评审确认：

| # | 问题 | 决定 | 考虑过的备选 |
|---|---|---|---|
| 1 | 同名账号在 0.1.x 里改过 URL | **两条都保留**，旧版的以「名称 (0.1.x)」导入。不丢数据，由用户确认后删掉无效的那条 | 直接替换新版里的 URL：列表更干净，但如果 0.1.x 里的改动是误操作，新版里原来的密钥就丢了 |
| 2 | 0.1.x 删除的账号 | **只告知**，用户自己去「管理」里删 | 提供「同时在新版里删除」的勾选框，默认不勾选：多一个批量删除入口，风险更高 |
| 3 | 提示方式 | **启动时弹窗**；选「稍后」后菜单最上方保留一项 | 只在菜单最上方显示：打扰更少，但用户可能注意不到 |
| 4 | I6 之前迁移、没有基线的安装（目前只有内测同事） | **静默记录基线**，不提示 | 对照 `accounts.json` 列出「`gp.secrets` 里有、新版里没有」的账号：会把在新版里删掉的账号也列出来，需要用户逐个判断 |
| 5 | `cleanup.sh` 遇到待导入的改动 | **醒目警告并列出账号，输入 `yes` 后仍可继续** | 拒绝清理，要求先处理：更安全，但用户确实不想要这些改动时会被卡住 |

## 8. 工作量

约 1 天：核心逻辑和单元测试半天，提示窗口和菜单项 0.3 天，脚本、文档和探针测试 0.2 天。

在中英文问题修完之后再做：I6 会给三个脚本新增提示语，那时脚本已经支持英文输出，新增的提示可以一次写好两种语言。
