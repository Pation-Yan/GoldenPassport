# 数据与接口兼容策略

GoldenPassport 保存的是 MFA 密钥。数据一旦丢失，用户可能被锁在自己的账号外面。所以任何版本的改动，都要先回答两个问题：**升级后旧数据还在不在**、**回退到旧版本后数据还在不在**。

本文规定：哪些东西属于兼容性契约、怎样改才算兼容、遇到不可逆的变更时怎样迁移，以及怎样告诉用户。

## 1. 兼容性契约

下面这些内容会被其他版本的 GoldenPassport、其他验证器或用户自己的脚本读取，修改时都要遵守本文。

| 对象 | 位置 / 形式 | 谁会读 | 当前格式 |
|---|---|---|---|
| 账号数据 | 数据目录 `accounts.json` | 0.2.x 各版本 | **数据格式 1**：JSON 数组，元素为 `{id, name, url}` |
| 设置 | 数据目录 `settings.json` | 0.2.x 各版本 | JSON 对象，所有字段可选 |
| 旧版数据 | 数据目录 `gp.secrets`、`config.plist` | 0.1.x；0.2.x 的迁移逻辑 | **数据格式 0**：NSKeyedArchiver `[String: String]`。0.2.x 从不修改内容，只把权限收紧为 `0600` |
| 旧版数据的基线 | 数据目录 `legacy-baseline.json` | 0.2.x 各版本 | JSON `{version: 1, source: "gp.secrets", recordedAt, entries: {名称: URL 指纹}}`，不含密钥和 URL（I6） |
| 备份导出 | 用户保存的 `.secrets` | 0.1.x 和所有新版本的「导入」 | 与数据格式 0 相同 |
| URL 列表导出 | 用户保存的 `.txt` | 任何支持 otpauth 的验证器 | 每行一条 otpauth URL |
| HTTP 接口 | `GET /`、`GET /code/<名称>` | 用户脚本、浏览器 | `/code/` 返回纯文本验证码；找不到时返回 404 |
| 发布信息 | GitHub Release 的 tag 和附件 `compat.json` | 0.2.0 起各版本的「检查更新」 | 见第 5 节 |
| 数据目录与 bundle id | `~/Library/Application Support/GoldenPassport`、`site.stanzhai.GoldenPassport` | 所有版本、安装脚本 | 保持不变 |

`--migrate-data` 的输出只给**同一个安装包**里的 `install.sh` 使用，两者总是一起发布，所以不属于跨版本契约。

## 2. 现有的保护

- **读不懂就停下**：启动时如果 `accounts.json` 存在但无法解析，程序会提示错误并退出，不会把它当成空列表，也就不会在下次保存时覆盖它。`AccountStore` 本身也会报错，不会返回空列表。还没迁移时，读不懂 `gp.secrets` 同样会停下，否则会生成一个空的 `accounts.json`，账号就再也不会迁移过来（`AccountStore.load`、`AppEnvironment.prepareDataDirectory`，测试为 `corruptAccountsFileIsAnError`、`unreadableFileThrowsAndIsLeftAlone`、`unreadableLegacyFileStopsMigration`）。
- **旧文件内容不变**：从 0.1.x 迁移时生成新的 `accounts.json`，`gp.secrets` 的内容保持原样（只收紧权限），所以装回 0.1.x 仍能看到迁移那一刻的全部账号。
- **安装前备份**：`install.sh` 会先完整备份 App 和数据目录，迁移后逐条核对，核对失败就自动恢复；`rollback.sh` 可以恢复备份。
- **回退提醒**：`rollback.sh` 回退后，如果数据目录里有 `accounts.json`，会提醒用户：新版里新增或修改的账号旧版看不到，需要的话先在新版里导出 `.secrets`，再导入旧版。
- **发现回退期间的改动**：从 0.1.x 迁移时记下 `gp.secrets` 的基线（每个账号的名称和 URL 指纹）。之后启动时如果 `gp.secrets` 和基线不同，就列出 0.1.x 新增、修改、删除的账号，由用户选择导入；导入只新增，不覆盖、不删除已有账号。`install.sh` 会列出这些改动，`cleanup.sh` 在删除前警告还没导入的账号（I6，测试见 `LegacyChangesTests`）。
- **设置文件容错**：`settings.json` 逐项解析，读不懂的文件改名保留，HTTP 服务默认关闭（3.4，测试为 `unknownValueResetsOnlyThatSetting`、`unreadableFileIsKeptNotOverwritten`、`upgradeKeepsTheOldHTTPAutoStart`）。
- **原子写入**：所有数据文件都先写到临时文件再替换，权限为 `0600`。程序崩溃不会留下写了一半的文件；断电等极端情况下仍可能留下不完整的文件，由「读不懂就停下」兜底。

## 3. 变更分类与规则

### 3.1 兼容变更：不升级数据格式

满足**全部**条件才算兼容变更：

1. 只新增字段，并且新增字段是**可选**的。旧数据里没有这个字段时，新版本必须能正常工作。
2. 旧版本读到含新字段的文件时能正常解析。Swift 的 `Codable` 默认会忽略未知字段，所以这一条通常成立。
3. **字段被旧版本丢掉也可以接受。** 旧版本保存文件时，会把它不认识的字段丢掉。如果用户升级后又装回旧版本，再升级回来，新字段的值就没了。只要丢失后只是退回默认行为（比如「图标颜色」），就可以接受；如果会导致账号无法使用，就**不算**兼容变更，按 3.2 处理。

给已有字段增加新的取值，也按这三条判断：

- **设置里的选项**（例如快捷键多一种组合）：旧版本读到不认识的取值时，只把这一项恢复默认（0.2.0 起逐项解析设置，见 3.4），下次保存时会用默认值替换它。和第 3 条一样，丢失后只能是退回默认行为。
- **账号的 otpauth URL**（例如支持 hotp 类型或新的 `algorithm`）：旧版本会把这条账号显示为「<无效密钥>」，但会原样保存，不会删除或改写。这种降级可以接受，Release 说明里要写明「这类账号需要新版本才能使用」。

兼容变更不需要迁移，在 Release 说明里正常描述即可。

### 3.2 不可逆变更：升级数据格式

字段改名、改类型、删除字段、改变结构，或者新增的字段一旦丢失会造成损害（例如加密后的密钥），都属于不可逆变更。规则如下：

1. **数据格式号加 1**，并写进新文件：`{"formatVersion": 2, "accounts": [...]}`。
2. **写到新文件名**（例如 `accounts-v2.json`）。**旧文件原样保留，以后不再写入**，做法和 0.2.0 对待 `gp.secrets` 一样。这样旧版本根本读不到新文件，也就不会误读或覆盖它。
3. **迁移只在首次启动时进行一次**：新文件不存在、旧文件存在时，从旧文件转换。转换后的数据要和旧文件**逐条核对**，核对逻辑放进 `MigrationCheck`，让 `install.sh` 能够检查。
4. **新文件读不懂时停下**：解析失败或 `formatVersion` 比程序支持的更高时，提示错误并退出，绝不当作空数据。
5. **加测试**：至少覆盖从每一个旧格式迁移、迁移后旧文件不变、新文件损坏时拒绝启动这三种情况。
6. **版本号**：数据格式升级的版本，次版本号至少加 1（如 0.2.x → 0.3.0），Release 说明必须写「升级须知」，`compat.json` 里的 `dataFormat` 同步加 1（第 5 节）。

### 3.3 回退到旧版本

按 3.2 的规则，回退到旧版本后，旧版本读到的是**升级那一刻**的旧文件。也就是说，升级后新增、修改的账号，在旧版本里看不到。新版本里的数据仍然完整保留在新文件中，再次升级时会继续使用。

反过来也一样：迁移只在新文件不存在时进行一次，**回退后在旧版本里做的修改，不会自动带到新版本**。对 0.1.x 的做法是：迁移时记下旧文件的基线，之后启动时发现旧文件和基线不同，就列出这些改动，由用户选择导入，`install.sh` 和 `cleanup.sh` 也会提示（I6，见第 2 节）。以后每次升级数据格式，都要为被取代的旧文件做同样的事，`legacy-baseline.json` 的 `source` 字段就是为此预留的。

需要配套做的事：

- Release 说明的「升级须知」写明这两个方向；
- `rollback.sh` 已经对 0.1.x 给出提醒（第 2 节）。以后出现新格式文件时，同样要提醒：回退后看到的是升级前的数据；如果需要新版本里改过的账号，先在新版本里**导出**，回退后再导入（I5）。

### 3.4 设置文件

`settings.json` 里没有密钥，读不懂时不拒绝启动，但要满足两条要求：

1. **默认值要安全**：会扩大暴露面的设置，默认必须是关闭。目前只有「启动时同时开启 HTTP 服务」这一项：没有这一项或读不懂时，一律按关闭处理。
2. **逐项解析，不覆盖读不懂的文件**：
   - 某一项的值读不懂时（例如新版本给快捷键加了一种组合，用户又装回旧版本），只有这一项恢复默认，其他设置照常使用；
   - 整个文件都读不懂时，这次运行使用默认设置。第一次保存设置之前，先把原文件改名为 `settings.json.unreadable-<时间>` 保留下来，不直接覆盖。

**改默认值时，已有用户的行为不能悄悄改变**：迁移或升级时，要把旧的有效值显式写进设置文件。例如 0.2.0 把 HTTP 服务改为默认关闭，但从 0.1.x 升级的用户保持原来的设置（0.1.x 里没改过就是开启），否则依赖 HTTP 接口的脚本会在升级后突然失效。

设置结构有不兼容的改动时，换一个新的字段名，不要改变已有字段的类型或含义。

### 3.5 导出格式和 HTTP 接口

- **`.secrets` 导出要一直能被 0.1.x 导入**，它是用户在任何两个版本之间迁移数据的退路。确实要改时，新增一种导出格式，旧格式继续保留。
- **`.txt` 导出遵循 otpauth URL 标准**，不加私有扩展。
- **HTTP 接口**：现有路径和返回内容不改。需要新功能时新增路径；确实要改时，在 Release 说明里列为不兼容变更。

## 4. 迁移工具策略

目前**不单独做迁移工具**。已有的工具足以覆盖：

| 场景 | 工具 |
|---|---|
| 升级时转换数据格式 | App 首次启动时自动迁移，`--migrate-data` 负责核对 |
| 升级出问题 | `install.sh` 核对失败时自动恢复；`rollback.sh` 恢复备份 |
| 在任意两个版本、两台机器之间迁移 | `.secrets` 导出 / 导入，`.txt` 导出 |

第一次出现不可逆变更时，在 `--migrate-data` 里加上对应的迁移和核对，再评估是否需要独立工具。

## 5. 发布时的兼容性信息

「检查更新」通过 GitHub 的 `releases/latest` 接口找到最新的正式版，再读取这个 Release 的附件 `compat.json`，判断升级时要不要额外提醒。

### 5.1 tag 和 Release

- tag 一律写成 `v<主版本>.<次版本>.<修订号>`，例如 `v0.2.1`。旧版本靠它比较版本号。
- 预发布版本（beta 等）必须勾选 **Set as a pre-release**。`releases/latest` 不返回预发布版本和草稿，普通用户就不会被提示升级到测试版。
- 「latest」要始终指向版本号最高的正式版，因为「检查更新」只看它。在旧的版本线上发补丁时（例如已经发布 0.3.0，再发 0.2.5），取消勾选 **Set as the latest release**。

### 5.2 compat.json

每个 Release 都上传一个名为 `compat.json` 的附件：

```json
{"dataFormat": 1, "minUpgradeFrom": null}
```

| 字段 | 含义 |
|---|---|
| `dataFormat` | 这个版本使用的账号数据格式号（目前是 1） |
| `minUpgradeFrom` | 能直接升级到这个版本的最低版本，例如 `"0.3.0"`。`null` 表示任何版本都能直接升级 |

用附件而不是写在 Release 说明里，是因为附件不会在编辑说明时被误删，客户端也不用从说明文字里去解析。以后要加字段，按 3.1 只加可选字段，客户端会忽略不认识的字段。

「检查更新」发现新版本后，按下面的规则提示用户：

| 情况 | 提示 |
|---|---|
| `dataFormat` 和本机相同，本机版本也不低于 `minUpgradeFrom` | 普通更新提示 |
| `dataFormat` 比本机高 | 额外提示：**升级后数据会转换为新格式，旧版本看不到升级后的改动。请先导出备份，再用 install.sh 安装，它会先备份数据。** |
| 本机版本低于 `minUpgradeFrom` | 提示：**不能直接升级，请先升级到 X**，并打开 X 的发布页面 |
| 没有 `compat.json`、缺少 `dataFormat`，或者下载、解析失败 | 仍然提示有新版本，并提醒：**无法确认兼容性，升级前请先阅读发布说明** |

只有确实需要分步升级时才设置 `minUpgradeFrom`，例如新版本删除了某个旧格式的迁移代码。按 3.2 的规则，新版本应当尽量保留对所有旧格式的迁移能力。

## 6. 发布前检查清单

每次发布前逐项确认：

- [ ] 这次改动是否涉及第 1 节的任何对象？涉及的话，属于 3.1 还是 3.2？
- [ ] 不可逆变更：数据格式号、新文件名、迁移、核对和测试是否都已完成？
- [ ] 不可逆变更：是否写了「升级须知」，并说明了回退后两个方向的行为（3.3）？
- [ ] 不可逆变更：是否为被取代的旧文件记录基线，再次升级时能提示回退期间的改动（3.3）？
- [ ] 改了默认值吗？已有用户的行为是否保持不变（3.4）？
- [ ] tag 是否为 `vX.Y.Z`？预发布版本是否勾选了 pre-release？「latest」是否指向版本号最高的正式版？
- [ ] 是否上传了 `compat.json`，内容是否和这个版本一致？
